# yedam.kr 자체 서버 이전 방안

작성 2026-08-08 · 대상 저장소 `yedam-website` · 범위 **도메인(yedam.kr) 등록·DNS는 그대로 두고 나머지 전부**

---

## 1. 지금 어디에 무엇이 있나

전수 조사(93개 배포 파일 · 7.59 MB) 결과, 외부에 남아 있는 것은 **네 곳**이다.

| # | 서비스 | 하는 일 | 이전 난이도 | 비고 |
|---|---|---|---|---|
| 1 | **GitHub Pages** | 정적 파일 호스팅 | 쉬움 | 빌드 단계가 아예 없음 |
| 2 | **Cloudflare Worker** `lucky-sun-025e` | AI 대화 · 감정분석 · STT · OCR · 정부 API 프록시 | 쉬움 | 표준 `fetch`만 사용 |
| 3 | **Supabase** `ushtyxnmqclzgdnynusm` | Google 로그인 · 프로필/조직/결과 DB · RPC 10종 · Edge Function 2종 | **어려움** | 인증 전면 재작성 필요 |
| 4 | ~~Netlify~~ | 결과 저장 API | **이미 이전 완료** | 구버전 파일에만 잔재 |

이미 자체 서버가 돌고 있다. `api.yedam.kr` = IDC Windows Server 2025(218.234.18.45) · Node 24(`127.0.0.1:8787`) · PostgreSQL `yedam` DB · Cloudflare Tunnel로 HTTPS 노출. 결과 183행이 적재돼 있다. **즉 이전은 "처음부터"가 아니라 "이어서"다.**

가장 유리한 조건 하나. 빌드 도구가 없다. `package.json`도 번들러도 워크플로도 없고, Tailwind·Chart.js·supabase-js 모두 CDN에서 런타임에 불러온다. **어떤 웹서버든 파일만 올리면 그대로 뜬다.**

## 2. 단계별 계획

쉬운 것부터, 각 단계가 끝날 때마다 서비스가 살아 있도록 순서를 잡았다.

### 1단계 — Worker를 자체 Node로 (1~2일)

`_backup/cloudflare/worker.js` 102줄이 전부다. 표준 `fetch`·`Request`·`Response`만 쓰므로 Node 24에서 거의 무수정으로 돈다. 데이터가 없어 마이그레이션도 없다.

- `api.yedam.kr`에 `/ai/*` 경로를 추가해 같은 로직을 태운다
- 프론트 4곳의 주소만 바꾼다 — `aipia/test.html:2716, 3317, 5034` · `career.html:103`
- **키 10종은 전부 재발급해야 한다.** Cloudflare Secret은 값을 다시 볼 수 없다
  (`GEMINI_KEY` `GROQ_KEY` `CEREBRAS_KEY` `OPENROUTER_KEY` `HF_KEY` `GITHUB_KEY` `CAREERNET_KEY` `DATAGO_KEY` `KOSIS_KEY` `PROXY_TOKEN`)
- 커리어넷·NEIS는 CORS를 막아 두어 **프록시가 없으면 진로·급식·시간표 기능이 통째로 멈춘다.** 이 단계를 건너뛸 수 없다

### 2단계 — CDN을 로컬 번들로 (1일)

폐쇄망이거나 외부망이 끊기면 화면이 붕괴한다. 특히 `cdn.tailwindcss.com`(6곳)이 죽으면 AI PIA 검사 화면 레이아웃이 전부 깨진다.

| 대상 | 건수 | 죽으면 |
|---|---:|---|
| `fonts.googleapis.com` / `gstatic` | 73 | 글꼴이 통째로 바뀜 |
| `cdn.tailwindcss.com` | 6 | **레이아웃 전면 붕괴** |
| `cdn.jsdelivr.net` (supabase-js · chart.js · HF) | 19 | 로그인·결과저장·그래프 정지 |
| `cdnjs.cloudflare.com` (qrcodejs) | 1 | QR 생성 정지 |

함정 하나. `login.html:55`에 `integrity="sha384-..."` SRI 해시가 걸려 있다. **로컬 파일로 바꾸면서 `integrity` 속성을 같이 지우지 않으면 브라우저가 로드를 차단한다.**

### 3단계 — 결과 API 마무리 (0.5일)

서버는 이미 돌고 있고 보안 마감만 남았다.

- `ALLOW_ORIGINS`가 아직 `*` → `https://yedam.kr`로 좁히기
- `POST /api/results`가 **무인증** → `INGEST_TOKEN` 켜기 (지금은 누구나 가짜 결과를 넣을 수 있다)
- 관리자 비밀번호가 **GET 쿼리스트링**으로 오간다(`results-admin.html:300~567`) → 헤더/POST로 이전. 서버 로그와 브라우저 히스토리에 평문으로 남는다
- 삭제도 GET(`results-admin.html:560`) → POST/DELETE로

### 4단계 — Supabase를 자체 PostgreSQL로 (2~3주) ★ 최대 난관

여기가 전체 일정의 대부분이다.

- **Google OAuth 재설정**: 현 콜백이 `ushtyxnmqclzgdnynusm.supabase.co/auth/v1/callback`이다. Google Cloud Console의 승인 리디렉션 URI를 자체 콜백으로 바꾸고, 세션·JWT 발급을 직접 구현해야 한다
- **RPC 10종 이식**: `pia_my_profile` `pia_org_by_code` `pia_percentile` `pia_class_results` `pia_recent_errors` `pia_recent_inquiries` `pia_link_parent` `pia_join_org` `pia_create_org` 등 SECURITY DEFINER 함수
- **Edge Function 2종**: `careernet` · `delete-account`
- **RLS 14종**을 애플리케이션 레벨 권한 검사로 옮기기
- **하드코딩 정리**: Supabase URL·anon key가 **11개 파일**에 박혀 있다. 설정 파일 한 곳으로 뽑아내지 않으면 11곳을 각각 고쳐야 한다

권한 역할은 `individual` / `org_member` / `org_admin` / `super_admin` 네 가지다.

### 5단계 — 정적 파일을 IIS/Nginx로 (0.5일)

- `.nojekyll` · `CNAME`은 불필요 — 삭제
- `404.html` 추가 (지금 없다)
- **구 도메인에 서비스워커 폐기 스크립트를 먼저 배포**한다. `sw.js`의 `yedam-cache-v4`가 방문자 브라우저에 남아 옛 화면을 계속 서빙한다
- DNS 전환은 마지막

## 3. 이전 "전에" 결론이 필요한 것 — 보안 3건

이전 작업과 별개로, 옮기기 전에 판단이 필요하다.

**① 동의 이력이 서버에 안 남고 있다.** `aipia/test.html:8704, 11528`이 `sb.rpc('pia_log_consent')`를 부르는데 **DB에 그 함수가 없다.** `try/catch`에 `.catch()`도 없어 실패해도 아무 표시가 없다. 동의는 지금 `localStorage`에만 남는다. 개인정보보호법상 입증자료라 그냥 넘길 수 없다.

**② Supabase RLS에 권한 상승 경로가 있다.** `CREATE POLICY "org read" ... USING (true)`로 조직 코드가 전체 공개 → `pia_join_org`가 승인 없이 `role_status='active'`를 부여 → `pia_class_results`로 학생 결과를 열람할 수 있다. **결과에는 자해 문항(`phqa.selfHarm`)이 포함된다.** 현재 organizations 테이블이 0행이라 발현되지 않았을 뿐이다. **학교 영업 전에 반드시 막아야 한다.**

**③ NEIS 키가 공개 저장소에 노출돼 있다.** `nice-timetable.html:200` · `teacher-meal.html:102`에 평문. 재발급 후 프록시 Secret으로 옮긴다.

부수적으로 정리할 것 — 구버전 `ai-pia2.html` · `ai-pia3.html`(966 KB)이 죽은 Netlify 주소를 계속 보고 있다. 삭제 여부 결정 필요. `_backup/` 폴더에 실제 학생 데이터 199개 JSON(9.6 MB)이 평문으로 남아 있다(git 미추적, 이 PC에만 존재).

## 4. 무중단 전환에 쓸 수 있는 구조

다행히 결과 API 주소는 **코드 수정 없이 바꿀 수 있게** 짜여 있다.

```
localStorage.pia_api_base
  aipia/test.html:8262 · parent.html:69 · results-admin.html:270
```

한 대의 키오스크에서 이 값만 새 서버로 바꿔 검증하고, 문제없으면 기본값을 바꾸는 방식으로 단계 전환이 가능하다.

## 5. 일정 요약

| 단계 | 기간 | 서비스 영향 |
|---|---|---|
| 1. Worker → 자체 Node | 1~2일 | 없음 (주소만 교체) |
| 2. CDN 로컬 번들 | 1일 | 없음 |
| 3. 결과 API 보안 마감 | 0.5일 | 없음 |
| 4. Supabase → 자체 DB | **2~3주** | 로그인 일시 중단 구간 발생 |
| 5. 정적 호스팅 이전 | 0.5일 | DNS 전파 중 혼재 |

**1~3단계만 해도 외부 의존이 Supabase 하나로 줄어든다.** 4단계는 규모가 크므로 별도 판단이 필요하다.

---

## 6. 롤백

각 단계는 되돌릴 수 있게 잡았다.

- 1단계: 프론트 주소 4곳을 Worker로 되돌리면 즉시 복구. Worker는 지우지 않고 남겨 둔다
- 3단계: 서버 환경변수만 원복
- 5단계: DNS를 GitHub Pages로 되돌린다. 저장소는 그대로 두므로 항상 살아 있다
- 4단계만 되돌리기 어렵다. Supabase 프로젝트를 최소 1개월 유지하고, 전환 후에도 읽기 전용으로 남겨 둔다
